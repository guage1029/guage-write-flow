# style-guide.md — 写作风格规范

> 本文件固定 Markdown 标题语法与瓜哥口语声线，不固定章节主题和叙事顺序。本文件是持续维护的风格手册，具体声音规则集中写在这里；persona.md 提供身份与读者背景。用户本次要求与事实准确性始终优先于口语和传播效果。

## 固定 Markdown 格式

完整长文按以下标题层级输出。固定的是格式，不是章节主题：

```markdown
# 主标题

可选副标题（普通段落，不使用标题标记）

开篇正文，不另设“引言”标题。

## 主要章节

### 需要时使用的子章节

#### 仅在确有必要时使用，并按同一父级连续标记 ①、②、③……
```

- 全文恰好一个 `#` 主标题；完整长文至少一个 `##` 主要章节。
- 主要章节使用 `##`，子章节使用 `###`；`####` 仅在确有必要时使用，并按同一父级连续编号 `①、②、③……`。严禁从 `##` 直接跳级到 `####`，禁止 `#####` 及更深层级。
- 开篇直接进触发点、反差或结论，不另设“引言”；章节名与结尾随本篇内容自然命名或收束，不套用固定的“背景 / 原理 / 总结”或“写在最后”模板。

## 瓜哥声音校准

以本手册的具体改写规则和 `persona.md` 的作者定位作为新写文章的默认目标，尽可能贴近瓜哥当面讲述的自然口语，不满足于“清晰但像通用技术说明”。

- **先找到本篇抓手**：从行业反差、读者常见疑惑、作者亲手卡过的坑或一个反常识结果开局；开篇只负责把人带进来并亮明本篇边界，不写成“本文基于……拆清几件事”的工作汇报。
- **在场感靠真实动作，不伪造亲历**：实测稿写清在哪卡住、改了什么做法才继续推进，并如实交代失败尝试与干预。无亲测时直接呈现资料比对、条件拆解与有依据的判断，不补造“我测了/我发现”或作者阅读经历，也不预设资料中必有隐藏限制。
- **用动作解释技术差异**：有对比材料时，可以先给数字或现象，再讲各自实际做了什么，最后解释这对读者意味着什么。顺序随材料调整，不要求每个机制都套用同一结构，不限定判断句字数；必要的解释和限定不能为了短而删掉。
- **读起来像熟人聊天，评价跟着证据走**：优先主动句与常用词，允许有依据的直白短评；不靠堆口头禅、密集感叹号或网络热梗造人味。局部成绩与整体推荐分开判断，证据支持时可肯定也可保留，不强找慢、贵、额度少等缺点。
- **接住读者追问**：从结果转向使用、门槛或选型时，需要时把读者可能的问题说出来，再给回应与动作。问题不一定是抱怨；设想对话须保持设想语境，不冒充真实采访或用户反馈。
- **把抽象成本换算成可理解的工作量**：有真实记录或明确计算依据时，说明配额或耗时对应哪些任务，以及所含讨论、重试和执行范围；不同任务的复杂度不能混作统一产量。没有依据时保留原始计量，不编造每周能做几个任务。

**输出前自检：** 去掉强形容词、加粗和口头禅后，文章是否仍有清楚的问题、可核验依据、作者自己的判断？若没有，先补清依据或收窄判断。

**阻断规则：** 新写长文的口吻校准与固定格式必须全部通过才可交付；AI 风格 P0 必须清零，P1 必须改成自然、具体的表达；不能以脚本全绿作为免审理由。

**风格与事实分开：** 绝对不照搬样文中的具体测试数据、经历、错漏字或跳级排版。已有文章降 AI 味时，优先保护原作者声音，除非用户明确要求改写成瓜哥口吻。

## 精细改写是必选项

- **初稿与改写必须分离**：新写长文无论首稿自评或机械检查结果如何，都必须冻结 `draft.md` 后进入独立逐段风格改写与全文复查，按 `style-review.md` 留存对照。
- **全量处理，不设数量配额**：逐段审查开篇、转场、解释、列表说明与结尾，有多少问题改多少，不设 3–5 处或固定轮数；原本合格的段落实审后可保留并说明理由。

### 四类 AI 味顽疾拆改法（Rewrite Playbook）

1. **开篇去空洞导语**：检查预告句是否重复标题或延迟进入具体问题，必要时改成触发点、结果或疑问，并交代本篇依据与边界。结果前置和有实际信息的摘要可以保留，不把本篇的发布反差开头推广成固定模板。
2. **中段去机械总起**：编号、加粗和“第一是 / 第二是”如果只增加标签、不增加信息，就改成直接解释的自然段落。真实步骤、清单、并列判断和便于扫读的总结可以保留；检查它们是否帮助理解，不按形式一律删除，也不把全部解释都改成“数字—动作—判断”三段式。
3. **拆解妨碍理解的长句与括号**：检查长定语、分号串联或括号是否打断主句、塞入多个不同层次的意思。影响理解时拆句或调整位置；必要术语、来源与口径说明可以保留。不按括号字数、层数或子句数量一刀切，不把限定条件移远或删掉。
4. **结尾去空洞拔高与硬夸腔**：根据实际证据给出判断、下一步动作或适用边界。结论可以正面、负面或保留，不强凑宏大建议，也不把“没那么惊艳、换个模型”等单篇结论套到其他题材。

### 高频局部块避坑点

- **标题下方第一句**：避免只复述小标题的垫话；需要交代阅读顺序、背景或限定时可以承接，再进入具体内容。
- **表格前后**：交代比较对象、来源和口径，按读者需要解释关键差异及其含义，避免逐行重复已有信息；不限定说明句数或解释条数。
- **避坑与选型小节**：禁止每条都套成字数对称的“现象—原因—建议”三段式，按实际轻重决定长短。

## 结构、节奏与段落呼吸

- **短段为主，推理保持完整**：以微信手机端好读为准，一段主要承载一个意思；关键结果或读者问题需要停顿时可以独立成段，连续机制解释允许稍长。不固定每段句数，不把全文切成同样长短的碎句。
- **让结构跟着素材走**：不预先往文章硬套固定的章节数和字数；转场直接说下一步看什么或替读者抛出下一个疑问，少用“看懂 X 后，再看 Y”这类过渡垫话。
- **克制加粗与排版信号**：加粗服务扫读，反引号用于代码、标识符等合适对象；不要求每段加粗，也不机械地给每条总起句加粗。引用块用于确有必要单独呈现的原话或判断，不固定绑定反转句。
- **朗读复查**：改完从头到尾默读一遍，遇到翻译腔、书面长定语、不自然停顿或报告腔立即拆成短句重写；代码、来源链接与限制条件保持真实。

## 证据与表达边界

- 区分日志事实、实测结果、个人推断和一般结论，并写清测试范围与来源口径。
- 没有同题基线，不比较快慢、准确率或优劣；日志未记录到的结局，不写成已通关或已成功。
- “请求成功 / 返回合法选项 / 完成任务 / 结果更好”是不同层级的结论，不得互相替代。
- 不把口语化当成弱化证据或省略限定的理由；未经验证的结论缩小范围、加限定或列为待核实。

## 文章类型参考（按需组织，不照抄模板）

- **实测 / 案例**：为什么做 → 怎么试与中途卡点 → 难度递增的案例与日志 → 数据支持的边界 → 分场景选型与坦诚体感。
- **资料解析（`source-analysis`，一般组织参考，待对应作者样文校准）**：围绕读者问题呈现资料、关键条件与分析判断；有比较、成本或迁移问题时再展开，不预设每篇都有最新变化、误判或暗坑。
- **教程**：目标与前置条件 → 操作步骤 → 预期结果 → 常见错误与处理。
- **经验分享**：遇到的问题 → 试过的办法 → 结果与代价 → 给读者的建议。

## 避免的表达

- 助手式开场白、万能总结、空泛的意义拔高和无依据的绝对化结论。
- 为制造悬念或人味而虚构冲突、时间、对话、情绪、“很多团队第一反应”等无依据群体断言，以及没有素材支撑的“我试了一圈”。
- 连续套用“首先、其次、最后”、整齐三段式、每节金句或固定三条结论。
- 把简单事实扩写成教程腔、评测报告腔或产品宣传文案。

### 失败过程：通过真实调整建立在场感

定位：「第二部分／第一回合：单文件原型，Flash 一次写成」，输出中断后的处理与耗时说明。

> 我把任务改成先写页面结构、再补脚本

> 把前面的失败尝试也算上

- **学习什么**：用具体动作交代如何调整做法，把失败尝试与后续完成放回同一过程解释，作者的判断有操作依据。
- **不照搬什么**：不把“先写结构再补脚本”当成所有任务的解法，不移用样文耗时，也不为增加人味编造一次失败或干预。

### 机制解释：从双方的动作讲清差异

定位：「第二部分／第三回合：双蛇对战」，查看两边代码之后的解释。

> `Flash` 主要看下一步能走到多少空地；`Argon` 会多往后推演几步，也会估算挡路的蛇身什么时候缩走。

> 简单说，`Argon` 所控制的 `Bot` 想得更远，也更会判断前面是不是死路。

- **学习什么**：先把机制说成读者能理解的具体动作，再解释这意味着什么；短评建立在前面的解释上。句长服从把意思说清楚，不压成固定字数。
- **不照搬什么**：这些能力描述只属于该篇提供的案例，不能移用到新模型或新任务；不要求每段都出现“简单说”或都以双边对比展开。

### 局部结果与总体感受：评价范围分开

定位：「第一部分／第三轮结果」与「第六部分／写在最后」。以下是两个不同位置的片段，不是连续段落。

> 最终 `Argon` 以 **56%** 的胜率获得冠军。

> 经过两周的实际使用`Gemini 4 Argon`，我并没有感觉到眼前一亮。

- **学习什么**：局部比赛成绩与长期使用感受可以分别成立；说明各自依据和范围，再让读者结合任务、场景与期待作选择。
- **不照搬什么**：不把该篇胜率、使用时长或“不惊艳”当成默认结论，也不要求其他文章必须找缺点才能显得克制。

## 持续迭代风格手册（每次执行必做复盘）

1. **执行前吸收反馈。** 检查本任务中用户明确指出的表达偏好、亲自修改的段落，以及明确指定可作为风格依据的本人样文。用户确认选题、骨架或事实，不等于认可文章口吻。
2. **把可复用的修正写回本文件。** 先定位现有规则，优先修订、合并和去重；确有新维度时再添加。记录反馈日期、消息或样文位置、用户原意、适用范围和例外。题材专属要求保持局部，不升级为所有文章的统一模板。
3. **区分确认与自评。** 模型生成的改写、自己的审校高分、脚本通过、尚未被用户认可的候选句，都不能直接当作瓜哥已确认的写法。
4. **每轮必须有复盘结论，不要求无依据地改文件。** 有明确依据则实际修订手册并按新规则复查当前稿；没有新依据时保留规则，在审校报告说明“本轮复盘，无新增已确认风格依据”。
5. **反馈触发重写。** 用户说“还是不像我”或指出报告腔时，不能只补几处口头禅；先更新相应规则，再对所有受影响段落重写并全文复查。不能保证已解决时如实说明差距，不将待校准稿冒充终稿。
6. **维护边界。** 已获用户持续维护授权时按以上依据更新本手册；未授权时报告拟更新内容，不自行持久化。更新 Skill 版本时只递增补丁号 0.0.1。安装目录不可写时明确报告未持久化及待合并规则；不自动公开或推送用户反馈与私人样文。
